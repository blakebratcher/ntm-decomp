# M1 (Z80 sound driver) — architecture notes


`200-m1.m1` is 128 KiB. Per the MAME driver (`neogeo.cpp`, audio_map):

- Z80 `0x0000-0x7fff` = the first 32 KiB of the M1, fixed
  (`m_bank_audio_main`).
- `0x8000-0xbfff`, `0xc000-0xdfff`, `0xe000-0xefff`, `0xf000-0xf7ff` are
  NEO-ZMC bank windows (16/8/4/2 KiB granularity; the Z80 selects banks by
  writing the latch port `$18`, mirrored from the audio-latch path).
- `0xf800-0xffff` = Z80 RAM (`$f800` frame counter, `$f801/$f802` command
  counters, `$f80a` YM status shadow, `$f80b` port/register scratch).
- Ports: `$00` sound latch (68k command), `$04-07` YM2610, `$08` bank
  select / NMI enable, `$0c` sound latch 2.

## Decoded layout

The M1 contains 18 functions and 310 flow-recovered blocks. The decoded entry
points cover reset and vector dispatch, YM2610 initialization and per-tick
service, a command queue and NMI dispatcher, and per-frame service routines.
The bulk of the image beyond these entry points is compressed data.

Per-routine instruction-level details are part of the source corpus; the
public tree keeps the behavioral summary and the classification metadata.

## Driver family (identified 2026-10-11)

The M1 carries no plaintext signature (no `MAKOTO` / `Mr.Pac` /
`Sound Driver` / `to SK` strings), and the NeoGeo Dev Wiki's
[Sound drivers list](https://wiki.neogeodev.org/index.php?title=Sound_drivers_list)
likewise records none for this title. Identification therefore went by
byte-level comparison instead: `tools/m1_family_scan.py` measures 16-byte-
window sharing between this M1 and other sets' M1s over the driver code
window (`0x0000-0x6000`).

| Candidate (local set) | Signature | Code-window share |
|---|---|---|
| Metal Slug (`201-m1.m1`, Nazca 1996, unsigned) | none | **92.7%** |
| The King of Fighters '94 (`055-m1.m1`) | `Ver 3.0 by MAKOTO.04/03/10 to SK` | 7.2% |
| Samurai Shodown (`045-m1.m1`) | same MAKOTO 3.0 string | 7.6% |
| Fatal Fury (`033-m1.m1`) | `Ver 2.0a by MAKOTO.03/04/05 to SK` | 7.8% |
| Blazing Star (`239-m1.m1`) | `Ver 2.0 by Mr.Pac h Ber.02/02/14` | 7.9% |
| KOF '98 (`242-m1.m1`) | `Sound Driver(ROM)Ver 1.7 98/06/16 To SNK` | 8.5% |
| Garou (`253-m1.m1`) | `Sound Driver(ROM)Ver 1.8 99/08/04 To SNK` | 6.1% |

The 6-9% cross-family "sharing" is low-entropy coincidence: a 19,762-byte
run at `0x1b2ce-0x20000` with only two distinct byte values (padding) plus
sub-KB periodic data blocks; none of it is driver code. The Metal Slug
comparison instead shares ~22.8 KB of the 24 KB code window in three long
runs (`0x0c6-0x24df`, `0x2502-0x37d7`, `0x3e36-0x57e9`) - and both are
Nazca 1996 titles. Conclusion: this driver is the Nazca in-house code base
shared with Metal Slug, not a member of the signed MAKOTO / Mr.Pac /
"Sound Driver" families. Re-run the scan against any other local sets with
`tools/m1_family_scan.py the rebuild <zip>...`.

## Import conventions (unidasm → vasm z80/std)

vasm's std syntax differs from unidasm output: `.org 0x…` (not `org $…`),
`0x` hex (not `$`), and no `-no-opt` (the z80 module has no optimizer).
unidasm prints `jr` targets **relative to the dump base**, not absolute —
convert with `target = dump_base + displayed` (the ROM bytes are ground
truth, as always). The rebuild gates the flat 128 KiB image byte-exactly
(`make m1-check`).
